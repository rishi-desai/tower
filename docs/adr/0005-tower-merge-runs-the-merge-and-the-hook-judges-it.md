# `tower merge` runs the merge itself, and the hook judges it by where the PR lands

GitHub groups PRs submitted as a stack (`feat2 -> feat1 -> main`, by git-spice or `gh stack`; plainly chained PRs stay separate) into a stack of its own, refuses `gh pr merge` for them, and merges them only through its asynchronous merge API: a `PUT .../merge-async`, then polling its status, for up to minutes. Merging a stacked PR also merges every unmerged PR below it onto the stack's base. So workers get one merge command, `tower merge [PR]` (`src/tower/merge.py`). An unstacked PR goes through `gh pr merge` as before. A stacked one goes through merge-async, only from the bottom of its stack (one PR per run, so one approval covers one PR), and its branch is deleted only once no open PR is based on it: GitHub moves the PR above onto the stack's base by itself, and deleting its base first may close it.

This is an exception to ADR 0001 (tower's scripts print GitHub writes; the agent runs them): `tower merge` makes the merge and the branch delete itself. Polling, then waiting for GitHub's retarget before the delete, doesn't fit printed commands: the agent would run three or more commands in a fixed order, the delete would get its own prompt (unlike `gh pr merge --delete-branch`), and running them in the wrong order closes the PR above. Instead, the approval hook recognises `tower merge` (also as `run-tower.py merge`, or interpreter code naming tower and merge) and judges it exactly like `gh pr merge`. ADR 0001's concern, a public change with no prompt, still holds, and the merge's approval covers its branch delete, as `--delete-branch`'s does.

The method follows the PR, with no setting: a merge commit for a stacked PR, for chained PRs (open PRs are based on its branch), and for one whose head other PRs were merged into (an integration branch such as `integration/a-plus` -> `main`, whose branch is kept), so commits that other branches hold are never rewritten; a squash for every other PR, as before. If the repo allows no merge commits: a squash (a rebase if squashes are off too), but never for an integration branch, which then isn't merged. A PR based on a chained branch whose own PR already merged is refused until it is moved, since its commits would stay on that branch.

A merge is judged by where the PR lands: its base, or for a stacked PR the stack's base. Judged by its own base, a PR based on `feat1` in a stack on `main` would pass under `personal` as `merge_to_branch`, while it puts itself and every PR below it on `main`. The hook reads the stack from `gh api repos/OWNER/REPO/pulls/N`, since `gh pr view` doesn't show it. That call replaces ADR 0004's `gh repo view`: still two gh calls, with the same "only for a merge that is the whole command" rule. A `gh api` write to `pulls/N/merge` or `pulls/N/merge-async` is a merge too, so it is judged the same way rather than as an unnamed `gh api` write.

## Considered options

- **Print the merge-async and delete commands for the agent (ADR 0001)**: every write visible in the transcript, but a multi-step sequence with polling in between, a separate prompt for the delete, and the wrong order closes PRs.
- **merge-async for every PR**: one code path, and GitHub now recommends it, but it drops gh's local-branch cleanup and changes the path workers use every day. Left for a later change.
- **Allow merging an upper PR (GitHub merges everything below it)**: one run per stack, but one approval would cover several PRs, and every branch merged would need the delete rules.
- **Squash every PR, stacked or not**: one method, but a squash rewrites the commits the PRs above hold (or, for an integration branch, the per-ticket commits), and GitHub rebases the PRs above a stacked merge whatever the method.
- **A setting for the method**: one more thing to configure, for a choice the PR's shape already makes.
- **Judge a stacked merge by the PR's own base**: what ADR 0004 assumed stacks would need, but with GitHub's own stacks no merge ever lands on a stack branch, so it would let merges into `main` through as `merge_to_branch`.
