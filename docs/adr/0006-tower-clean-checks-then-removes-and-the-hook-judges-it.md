# `tower clean` checks, then removes, and the hook judges it by `cleanup`

Cleanup deletes things: a worktree, its local branch, its branch on GitHub. So `tower clean [WORKTREE ...|--all]` (`src/tower/clean.py`) proves first that nothing would be lost, for each worktree: its PR is merged, its HEAD is the PR's head commit, `git status --porcelain` is empty, no stash entry is on its branch, its card doesn't say work goes on (running, needs-you, blocked: a reused branch), and live sessions (`claude agents --json`) show none busy or waiting there. Each check is read fresh when the command runs. A worktree that fails any check is reported with every failed check and left exactly as it was; the others in the same run are still cleaned, since each worktree is independent and `--all` would otherwise be blocked by any one dirty worktree. Sessions must come from live data: the event log only stands in for the hub's view, and a crashed or mid-approval session can read as idle there.

Like `tower merge` (ADR 0005), it runs the removal itself: closing terminals and removing the worktree through Orca (`orca terminal close --all`, `orca worktree rm`, without `--force`), or `git worktree remove` without Orca, then deleting the local branch only if it still points at the checked commit (`git update-ref -d`), deleting the GitHub branch with `tower merge`'s own rules (never while open PRs are based on it, never an integration branch, never once it moved), archiving the card to `Ledger/_archive/`, and `git pull --ff-only` in the main checkout. As one command, it can't run the removals out of order, and the branch delete is covered by the cleanup's approval as `--delete-branch`'s is by a merge's.

The approval hook judges it by the policy's `cleanup` key, as it judges `tower merge` by the merge keys. `tower clean --dry-run` runs every check and prints what would be removed, touching nothing, and never asks. So under `cleanup = "ask"` the hub runs `--dry-run`, shows that list, and runs the real command, which asks once; under `"auto"` it runs it straight away. `tower clean` itself never prompts: an agent's shell has no terminal to answer on, and you running it in your own terminal is your yes.

## Considered options

- **tower prompts y/N itself under `ask`**: one command lists and asks, but agents run it without a terminal, so the hub could never use it, and the policy would be enforced in two places.
- **Default to listing, `--yes` to remove**: the safe form by default, but the same words would then do different things under ask and auto.
- **All-or-nothing across every worktree named**: one approval covers exactly the list, but one worktree with a stray file would block cleaning every other one.
- **Accept the event log when live sessions can't be read**: cleanup would work without `claude agents --json`, but a session approving a command records nothing, and a removal can't be undone.
